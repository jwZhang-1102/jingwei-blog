## 写在前面

2026 年 8 月中到 10 月初，我在人保养老知识服务平台实习。平台一侧是云盘，一侧是基于 MaxKB 的智能体：云盘里的文件要同步、分段、向量化，问答时才能当知识库用。

刚进去时我还在对 RAG、分段、向量化、Celery 这些词。后面主线一直是同一条链路：云盘文件进消息队列，Celery 下载并分段，再写入同步表、文档和向量。我主要做了三块：向量化率与脏数据怎么算、校准对账怎么做、向量化任务为什么跑不动；另外独立做完问答页的「添加云盘文件」，并参与风控解析、估值邮件的联调。10 月又补了两处现场问题：弹窗第一次打开要等好几秒，以及知识库相关的问题也开始回复「无法回答」。

下文按「链路 → 我负责的 → 校准 → 选文件 → 踩坑 → 反思」展开。

## 项目在做什么

用户在云盘里点向量化，或在智能助手里选一批文件来问。智能体要回答的前提，是这些文件已经变成可检索的段落向量，而且云盘上的「现在还有哪些文件」和库里的「哪些算成功」对得上。

终期能讲清楚的能力大致是：

| 能力 | 说明 |
|------|------|
| 日常同步 | 云盘变更走变更队列，下载、分段、向量化后回写同步表 |
| 校准 | 按空间把现存文件对一遍，云盘已删、库里仍显示成功的清掉 |
| 向量化率 | 分子是云盘现存且同步成功的文件，分母是云盘现存文件 |
| 添加云盘文件 | 问答页按个人 / 部门 / 公司 / 群组选文件或文件夹，带入本次对话 |
| 风控 / 估值 | 按任务号解析抽取；按邮件主题回信。我参与联调与部分修复 |

需要说清边界：校准解决的是「名单对不上」，不替代日常的单文件变更；问答选文件只决定这次用哪些已向量化内容，不会现场把没向量化的文件补做完。

## 技术栈速览

| 层级 | 选型 |
|------|------|
| 智能体 | MaxKB（Python） |
| 消息 | Artemis，变更队列与校准队列分开 |
| 任务 | Celery + Redis（双桶限流后再投递） |
| 数据 | PostgreSQL，同步表 `disk_sync_file` |
| 向量 | 本地 Embedding 服务 |
| 问答选文件 | 智能体前端 + 云盘目录 / 鉴权接口 |

同步表里一条文件的身份是云盘文件 `id`，对应 `file_id`。状态大致是：待处理、成功、失败、处理中。页面上的「排队 / 成功 / 失败」要回到这张表和 Celery 里实际在跑的任务，两边经常不是同一件事。

## 我负责的模块

- **向量化率**：统一口径，避免「已向量化大于总文件数」
- **校准**：云盘按空间发现存文件，智能体用 Redis 名单扣账，超时仍留在名单里的视为已删除
- **向量化稳定性**：批量删除把队列堵死、超长分段写库失败、重启后的假成功、大表格和邮件附件把 worker 占满
- **添加云盘文件**：目录弹窗、鉴权范围、文件名编码，并部署到测试和生产；后来把首次打开从大约 3 秒压到大约 1.2 秒
- **检索失效**：文档和分段都在、同步仍是成功，向量却是空的，问答落到兜底回复
- **联调**：风控解析链路、估值邮件主题与损坏附件重试；文件对比的解析失败排查

导航式的产品界面和云盘本体由其他同事负责。我接触最深的是智能体这一侧：消费消息、写同步表、把任务送进 Celery，以及问答页怎么列出当前用户有权限的目录。

## 关键链路：校准怎么对账

几万个文件不适合递归调云盘目录接口再和知识库比。后来的做法是两张名单：

1. 云盘对某一类空间（个人 / 公司或部门 / 群组）点一次批量，5 个线程往对应的校准队列发消息，**一条消息一个对象**，只传元数据
2. 智能体按空间根（repo）在 Redis 里维护一份 B：同步表里这棵树下、尚未删除的 `file_id`
3. 每消费一条，就从 B 里扣掉这个 `file_id`，再决定跳过、正忙，还是入队向量化
4. 每个整点检查：某张 B 超过一小时没有新消息，剩下的 `file_id` 视为本轮云盘没发到，进入删除

结束标记曾经想过，也否掉了。发送进程可能在「文件发完、标记还没发出」时被杀掉，智能体会一直等。用「整点 + 空闲超过一小时」收尾，实际空闲时长落在一到两小时之间；超时之后才到的消息，再按「不在 B」的规则判断，而不是一律当新文件。

主键只用 `file_id`。同内容复用可以共用文档，统计时仍按文件各计一次，不按 hash 合并，否则多个文件会合成一条，向量化率又会歪。

9 月底补过一处：文件改名或移动后，失败、中断的同步行仍留着旧 `full_path`。校准消费时如果命中已有行，先用消息里的新路径覆盖（正在下载的不动，也不改 `update_date`），再决定跳过还是重新入队。路径是下载地址，表不改，后面所有重试都会去旧位置。已经成功的行只改路径，不重新向量化。

删文件也会让两个数字短暂对不上。云盘上的总文件数马上少 1，成功数要等删除消息进紧急桶、Celery 跑完 `delete_file_vector`，把同步行改成已删除并清掉文档，才会减下来。任务还在排队或没跑成时，页面上就是成功数比总数多 1。同步行不会物理删掉，只改状态。

## 关键链路：问答页添加云盘文件

交互接近在输入框旁加文件：弹窗顶上四个分类——个人、部门、公司、群组——下面是各自的目录树。文件和文件夹都能选，可以跨分类，选中后以标签形式留在输入框附近，上限先定 1000。

目录从哪来：

1. 公司文件路径固定，测试和生产的根不一样，所有用户相同
2. 个人、群组从鉴权接口拿当前用户有权限的空间
3. 部门一开始经常是空的：鉴权结果里没有部门 id。后来改为用云盘 session 查出用户，再走鉴权
4. 没有部门的用户不能按公司根去列「所有 `/1/` 下的目录」，否则会把应用文件等不属于他的目录扫进来

前端只改页面时，重新打包上传静态资源即可；鉴权和目录接口在后端，配置（公司根路径、session 查询地址）要和代码一起上。上生产时曾经整页文件夹都不显示，缺的是列表接口的一个参数，报错是函数收到了未预期的关键字参数。

## 第一次打开为什么慢

客户说生产上第一次点「添加云盘文件」要转好几秒。我先怀疑文件名里的 `%` 让云盘报错，再回退去查智能体自己的库。对不上：测试账号有大约 7800 个个人文件，生产这个账号只有大约 900 个，测试反而更快。生产同步表有十几万行，这次查询本地只花了几十毫秒。

慢在打云盘的那一串请求，而且是串行的。原来要点两次：先等空间列表大约 1.5 秒，再等目录大约 1.5 秒，加起来大约 3 秒。其中 `appinfo` 单独就要大约 0.7 秒，还必须等 `/user` 回来才能发，个人目录又必须等它拿到空间 id 和鉴权信息。测试和生产是同一套智能体代码，测试云盘每次返回本来就只有几百毫秒。

改动是把能重叠的重叠起来，并把第二次请求拿掉：

1. 同一工作线程里复用到云盘的 HTTPS 连接，鉴权、查用户、`appinfo` 并行
2. 已经认出的个人、部门、公司、群组不再重复打鉴权
3. 个人根目录放进空间接口一并返回，弹窗不再单独请求 `folders`
4. 进入对话页、还没点按钮时就先请求目录，点开时直接用缓存

生产上第一次打开从大约 3 秒降到大约 1.2 秒。剩下的时间仍是生产云盘 `appinfo` 那一段，智能体侧再并行也藏不住。前后端要一起上：只更新后端时，旧页面还会再请求一次目录，第一次会更慢。预加载这一步只改聊天页。

## 踩坑一：点两次校准，成功数先掉

一次校准会拆成两段任务：先下载分段，再向量化。同步表要等向量写完才是成功，中间是处理中。去重锁在下载任务结束就放开，向量化还排在队尾时，第二轮校准可以再投一份同步任务，并把上一轮已经写好的向量清掉重做。页面上就是成功数先掉，再慢慢涨回来。

只清空 Celery 再校准也不够。处理中的文件会被当成「正忙」跳过，队列里已经没有任务，页面上却一直不动。可用的顺序是：清掉相关队列，把僵死的处理中改回待处理，清掉去重锁或等它过期，然后再校准。成功且文档还在的行不要动。

## 踩坑二：看起来很慢，其实任务投不进去

现场有过「一天只成功两百来个，排队几乎不动」。往下看，批量删除文件夹时，Redis 扫描结果的解包写错了：本该遍历字段和值，代码遍历的是键字符串，二元解包失败。失败后消息被放回紧急桶并直接跳出本轮，普通桶全部排不上。日志里每天十几万次解包失败，Celery 投递接近 0。这不是向量化模型变慢，是新任务进不去。

修的是遍历方式，以及失败不要无上限放回、不要用一次失败饿死普通桶。同一时期还遇到超长表格段写不进段落字段，改成超过长度继续切。本地模型每次重启要重新加载大约 700MB，再叠加持续请求会把 CPU 打满；worker 并发从 10 调到 5 之后，向量化效率大约只少 4%，崩溃停了。

下载和向量化还挤在同一条队列里。文件下载完会落库，向量化任务再丢回队尾，从库里读内容，不在内存里攒文件。队很长时，前面的大任务占满并发，后面的小文件就一直排队。所以「下载完了」不等于「向量已经写上」。

## 踩坑三：成功、失败、打不开，各自看不同的字节

有几类「看起来像同一件事」的失败，根因完全不同：

| 现象 | 实际原因 |
|------|----------|
| 重启后显示向量化成功 | 状态先写成成功，段落并没有全部写入；分段默认状态 `n` 还曾被当成已忽略 |
| 深层目录打不开，文件名里带 `%` | `%` 被当成 URL 转义，接口返回非法编码序列 |
| 文件对比报 `BadZipFile`，客户本机能打开 | 智能体读到的字节不是合法 docx。docx 本质是 zip，文件头应是 `PK`；旧版 doc 的文件头 Word 能开，当前解析器不行。文件名里的空格不会造成这个结果 |
| 邮件 `.eml`、复杂 xlsx 把 worker 拖死 | 附件 base64 被当正文切成几千段；空白单元格和竖线空壳也入库。后来在建段前丢掉纯 base64，空壳行不入库，并给表格加行数、段数上限 |

文件大小闸门、「分段超过 100 段直接失败」都是现场临时手段，用来让队列还能往前走。闸门关掉之后，已经分好的段可以继续向量化，不必整文件重切。

## 踩坑四：同步仍是成功，向量已经没了

问答里配过一条兜底：检索不到知识库内容时，回复一段固定的「无法回答和知识库无关的内容」。配置测通之后我没再改。10 月初客户问知识库里明明有的问题，也走到了这句兜底。执行详情里检索命中是 0。

库里的状态是：文档还在，分段还在（几百段），同步表仍是成功，这个知识库的 embedding 是 0。另一个知识库还有大量向量，不是整库坏了。把这两份文档重新向量化之后，回复恢复。

向量化在代码里是先删再写：按知识库清空 embedding，或按分段先删再批量写入。删成功、后面没写完，就会留下「分段和同步成功都在、向量是 0」。后面没写完，常见是 Celery 卡住、重启、模型超时。9 月 29 日下午开始检索变空，当天有一批向量化任务，只有一条删除。清已删文件一般会把文档和同步记录一起改掉，对不上「文档还在、只是没向量」。

更麻烦的是这条空窗会自己维持下去。同步表已经是成功，校准和日常变更都会跳过，不会发现 embedding 其实空了。应用日志按天滚动，大约只留 7 天，等用户来问时，已经查不到当时是谁点的向量化、Celery 有没有报错。问答配置本身不会删向量。

## 小结与还可打磨的点

这段实习让我把「消息 → 任务队列 → 同步表状态 → 页面数字」串成一条能在测试和生产上核对的链路。自己接触最深的是：

1. 统计、对账、下载必须用同一套主键和同一条路径。文件名和 hash 都不能当身份
2. 先分清慢和卡死。解包失败后双桶空转，表现很像向量化变慢；弹窗转圈则要拆请求是串行还是文件太多
3. 同步表的「处理中」常常表示文件已经下载完、向量化还在队尾；「成功」也不等于向量还在
4. 第三方接口要看业务错误信息。文件不存在，和文件名编码失败，不是一类问题
5. 用户能打开文件，只说明他本地那份可读；解析器认的是文件头
6. 页面上的总数和成功数有时间差。云盘删文件是立刻的，智能体要等删除任务跑完才减成功数

如果继续做，我会优先让「同步成功但 embedding 为空」变成可发现的状态，而不是等用户提问才暴露；「正在处理」和「队列里已经没有任务」也该能看出来，避免再靠手工改同步表来解开校准。`appinfo` 那一段耗时在云盘侧，智能体只能用进页面就预取来把它挪到点击之前。
