## 写在前面

学期综合实训（约 2026.03–2026.06）里，我们做了 **LensFocus**：连接摄影师与顾客的约拍交易与内容社区平台。技术栈是 **微信小程序 + Spring Boot 3 + PostgreSQL**；登录用 JWT（HS512），会话与验证码落在 Redis。

我主要负责个人主页、文件上传、首页、社区、消息及管理端相关**后端接口**，中后期主导前后端联调与缺陷修复，并配置 / 维护 Jenkins 构建门禁、参与 Gerrit 代码评审。下文按「为什么做 → 关键链路 → 联调环境 → 踩坑 → 工程」展开。

## 为什么做：立项里的真实痛点

立项并不只是「再做一个社交 App」。组里有人同时做过模特和摄影师，痛点很具体：

| 痛点 | 现状 | 平台想补上的能力 |
|------|------|------------------|
| 获客低效 | 依赖小红书发帖/评论「盲找」 | 社区 + 需求广场 + 多维筛选 |
| 交易无保障 | 微信私聊易逃单、水单 | 套餐下单、履约与订单状态 |
| 安全顾虑 | 私房/旅拍/夜间拍摄风险高 | 实名、行程守护、敏感词等（规划与落地程度不一） |
| 价格不透明 | 私聊报价混乱 | 结构化套餐与展示 |

产品侧规划过内容社区、创作发布、即时通讯、交易中心、个人中心，以及信用分、纠纷判定、教程等差异化能力。**课程交付能跑通的主线**更接近：微信登录与角色分流（USER / PHOTOGRAPHER）→ 作品/套餐/社区 → 消息与订单相关能力 → 管理端配合运营。立项里的「智能推荐 / 资金托管闭环」更多是愿景，实际落地程度因模块而异。

对我来说，价值不只是「写完接口」，而是把下面四件事串成可上线验证的闭环：

1. 鉴权与用户身份  
2. 文件与静态资源  
3. 社区发帖等业务写库  
4. 小程序模拟器 / 真机联调  

## 技术栈速览

| 层级 | 选型 |
|------|------|
| 客户端 | 微信小程序 |

## 我负责的模块

- **个人主页 / 资料**：用户信息展示、头像路径规范化、角色（USER / PHOTOGRAPHER）联调  
- **文件上传**：按 category 分类落盘（avatar、post、portfolio、order、package 等）  
- **首页 / 社区 / 消息**：列表与互动相关后端，以及和前端对接  
- **管理端相关接口**：配合运营侧联调  
- **质量与协作**：补测试、过评审；本组 Jenkins 持续集成由我配置（Verify +1 后方可合入）  

优惠券、购物车、GPS 点位、订单支付全流程等模块在项目里也有，由其他同学负责；我的工作重心仍在上面列出的接口与联调。

## 关键链路一：JWT + Redis 鉴权

小程序侧常见路径是：`wx.login` 拿 `jsCode` → `POST /api/auth/wechat/register`（可带身份）→ 后续请求带 Token；启动时也可走 `/api/auth/verify` 校验会话。

登录成功后大致是：

1. `JwtUtil` 签发 JWT（算法 HS512，默认约 1 天；claims 含 openId、userId，管理员可带 `role=ADMIN`）  
2. Redis 写入 `auth:token:{整段JWT} → userId`，TTL 与过期对齐  
3. 短信验证码使用 `auth:sms:{phone}`，短 TTL  

后续请求带 `Authorization: Bearer <token>`：

- **TokenAuthenticationFilter**：优先 Redis 查 userId，没有再本地验签解析 JWT，写入 request 属性 `CURRENT_USER_ID`  
- **TokenInterceptor**：对非公开接口强制校验 JWT（拦未登录）  
- **业务层**：`CurrentUserService` 取当前用户  

两层分工可以记成：**Filter 负责「认出你是谁」，Interceptor 负责「没身份就不让进」**。

Redis 短暂不可用时，多数接口仍可退化为纯 JWT 解析；短信验证码与「服务端主动踢下线」会受影响。登出目前更多是前端清本地 token，服务端靠过期失效——这是明确的改进点（登出时删 Redis key）。

> 容易记反的一点：映射是 **token → userId**，不是 userId → token。

## 关键链路二：分类上传与发帖（泛型 CRUD）

社区「日常帖 / 需求帖」**没有**单独的 `/api/community/create`，而是走 **泛型 CRUD**：`POST /api/crud/post`。顺序是 **先上传、再写库**：

1. 进入发布页：未登录引导授权；按角色过滤选项（找模特、发作品仅摄影师可见）  
2. 选图后 `POST /api/files/upload/post`（需登录）  
3. 后端落相对路径，例如：`users/{userId}/post/{yyyy/MM/dd}/{file}.jpg`  
4. 再 `POST /api/crud/post` 写 `post` 表；`GenericCrudServiceImpl` 会补 `user_id`，需求帖校验角色  
5. 库内图片字段是 PostgreSQL **`TEXT[]`**，只存相对路径；展示时拼前缀  

帖子类型别混：

| 入口 | 落库 | 说明 |
|------|------|------|
| 发布日常 | `post`，`post_type=SHARE` | 日常分享 |
| 找摄影师 | `post`，需求类 | 顾客侧需求 |
| 找模特 | `post`，`FIND_MODEL` | 仅摄影师 |
| 发布作品 | **`portfolio`** | 不是帖子 |
| 拍摄点位 | 另一套页面/表 | 别说成写 `post` |

发帖成功后，前端打刷新标记，社区页在 **`onShow` 再拉 feed**——比空说「刷新一下就能看到」更准确。失败时前端会留本地草稿，避免用户白填一遍。

## 本地 API + 远程 NAS：混合联调

联调时最省事的环境是：

- **`baseUrl`**：指向本机后端（如 `http://局域网IP:8080`）  
- **`mediaOrigin`**：指向远程 CDN / NAS（如已部署的静态资源域名）  

展示公式可以记成：

```text
可访问 URL = mediaOrigin + "/uploads/" + 相对路径
```

前端用 `resolveMediaUrl` 统一拼接。这样本地改接口、查库时，**不必把整库图片搬回本机**；只有「上传」才依赖本机 `file.upload.path` 配置正确。

真机还要注意两套域名：

- **request 合法域名**：接口请求  
- **downloadFile 合法域名**：图片加载  

模拟器可关校验，真机关不掉合法域名时，就要配齐，否则会出现「接口有数据、图片空白」。

## 联调故事：契约比代码更先崩

项目前期接口文档不完整时，前后端容易各写各的：同一能力 **URL、参数名、返回体** 对不齐。我们后来的做法是：

1. **以后端实现为准**补齐接口说明（再进 Apifox）  
2. 前端对照文档改请求与解析  
3. 新功能尽量「先契约、再开发」  

统一返回体 `{ code, message, data }`（`ApiResponse`）很重要。用 AI 辅助写接口时，我踩过一次坑：生成代码自建了一套返回 DTO，评审时才改回统一外壳——**工具出草案，契约和规范必须人审**。

## 两个印象深的 Bug

### 1. 「我的」页：`id: null`，头像却还在

**现象**：个人资料渲染成 `{ id: null, openId: "" }`，昵称/头像却像有值。

**根因链**：

1. 封装请求时只看 HTTP 200，**不校验 `body.code`**  
2. `/api/users/me` 实际返回 `{ code: 500, data: null }`，前端仍当成功  
3. 页面把空字段写进视图；展示层又回退读本地缓存（如 `wx_user_profile_v1`），于是「看起来像登录了，业务身份却是空的」  

**修复方向**：业务成功以 `code === 200` 为准；失败走明确错误态；用接口返回的 `role` 同步本地 `userType`，而不是只信本地缓存。

顺带还会撞上：注册时选了摄影师，库里仍是 USER——早期微信注册 DTO 没接 `userType`/`role`，写死 USER；静默登录先建 USER、授权登录才更新身份时，第二步没带参就会一直错。

### 2. 真机日历少一天

上线前真机测试：摄影师主页档期日历本应一行 7 天，真机只显示 6 天，模拟器正常。

排查顺序：

1. 确认接口日期数据完整 → 排除后端  
2. 对比模拟器与真机样式 → 定位到格子宽度  
3. 根因：按约 `1/7` 均分宽度时，未把 padding / border 算进宽度，真机累计溢出  

修复：日期格子加 `box-sizing: border-box`，真机恢复 7 天。

收获：**多端问题不能只看模拟器**；排障顺序优先 **Network（打到哪、状态码、body）→ 鉴权 → 路径/域名/样式**。

## 工程实践

- 接口先用 **Apifox** 自测，再进模拟器 / 真机  
- **Gerrit** 代码评审（评论、多轮改、Verify）+ **Jenkins** 构建门禁  
- 自动化测试扩充到约 **400** 个用例（JUnit / MockMvc，JaCoCo；团队总量）  
- Spring 侧用得最多的，是默认 **单例 Bean**（如 `JwtUtil`、Filter）共享配置；登录 VO 用 **Builder** 组织多字段返回；Filter 继承 `OncePerRequestFilter`，骨架固定、业务写在钩子里  

## 小结与还可打磨的点

LensFocus 让我完整走了一轮「后端接口 → 鉴权与资源 → 小程序联调 → 门禁与测试 → 真机排障」。自己接触最深、也最想记下的是：

1. JWT + Redis 会话怎么配合（token → userId，Filter / Interceptor 分工）  
2. 上传相对路径 + CDN / NAS 展示（本地 API + 远程媒体）  
3. 发帖走泛型 CRUD：「先上传再写库」  
4. 联调冲突时用接口文档对齐契约；HTTP 200 ≠ 业务成功  

如果继续打磨，我会优先考虑：服务端登出失效（删 Redis key）、更细的权限矩阵（避免「整段 auth 路径误放行」这类债）、以及把高频读路径的缓存用得更扎实。
