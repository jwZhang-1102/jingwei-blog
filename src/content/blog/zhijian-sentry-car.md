## 写在前面

软件工程学期实训Ⅲ里，我们做了 **智检哨兵**：一台搭载 Jetson 的 Rosmaster 小车，在封闭区域里用 ROS2 自主导航，同时用视觉做异物巡检，并把告警留到鸿蒙 App 上查阅。仓库名是 `oh-ai-car-ros-app`。

我主要负责 **YOLO 巡检告警链路**（检测脚本、一键启停、事件服务）、**罗技 G29 同协议控车**、**音乐伴舞脚本**，以及和鸿蒙 App 在控车 / 视频 / 巡检页上的联调。导航建图与 App 主界面由其他同学负责；YOLO 权重也由同学提供，我做的是接入与工程化落地。

下文按「场景 → 架构 → 巡检链路 → 并行踩坑 → 遥控与伴舞 → 反思」展开。

## 项目做什么

场景对准仓库 / 机房 /实验室一类封闭区域：小车按地图走到目标点，途中识别异常目标（答辩主演示是 **瓶子**），本地告警并截图留痕，手机端可回看事件。

终期可演示的能力大致是：

| 能力 | 说明 |
|------|------|
| 自主导航 | Docker 内 Nav2（n1 / n2 / n3），RViz 设起点与目标 |
| 智能巡检 | YOLOv5 检出目标 → 蜂鸣 / 语音 → 截图 + `events.jsonl` |
| 鸿蒙 App | 网络配置、遥控 / 麦轮、视频、巡检事件列表（约 4s 刷新） |
| G29 方向盘 | PC 端脚本，经同一套 TCP 协议控车 |
| 音乐伴舞 | 播歌 + 底盘编排动作（展示用） |

需要说清边界：当前是 **模式切换**（巡防 / 遥控 / 伴舞），不是导航过程中的无缝热接管；危险区多边形、mission 航点编排等曾做过实验，**不是**终期 PPT 主交付路径。

## 技术栈速览

| 层级 | 选型 |
|------|------|
| 车端算力 | Jetson（Linux） |
| 导航 | ROS2 + Docker 内 Nav2 |
| 视觉巡检 | Python、OpenCV、YOLOv5（`yolov5s.pt`，COCO 预训练） |
| 事件服务 | Flask HTTP（6700） |
| 手机端 | OpenHarmony / ArkTS（DevEco Studio，API 12） |
| PC 端 | 罗技 G29 + pygame / winmm → TCP 控车 |

## 三端口架构

手机、PC 与小车在同一局域网。车端能力按端口拆开，比「一个大杂烩服务」好联调：

| 端口 | 协议 | 用途 |
|------|------|------|
| **6000** | TCP | App / G29 控车（帧格式见 `doc/ros_api.md`） |
| **6500** | HTTP MJPEG | 实时视频（如 `/index2`、`/video_feed`） |
| **6700** | HTTP | 巡检：`/health`、`/events`、`/snapshot/...` |

```text
OpenHarmony App ──TCP 6000──► 底盘遥控（ros/run）
             ──HTTP 6500◄── 视频推流
             ──HTTP 6700◄── 巡检事件 / 截图

PC + G29 ──────TCP 6000──► 同一套控车协议

Docker Nav2 ◄──雷达 / 底盘──► 自主走点
宿主机 YOLO ◄──USB 摄像头──► 边检边记（6700）
```

App 侧常见组合：

- **巡检模式**：只关心 6700，看告警列表与截图  
- **遥控 + 视频**：连 6000 + 6500（需先切到遥控通路）

## 我负责的模块

- **巡检后台**：`patrol_detector.py`（取帧 → 推理 → 连续帧确认 → 冷却 → 告警）、`patrol_server.py`（6700）、`start_patrol_host.sh` / `stop_patrol_host.sh`  
- **告警落盘**：截图进 `capture/patrol/`，事件追加写入 `events.jsonl`  
- **G29**：`tools/logitech_g29_drive.py`，踏板模式映射到与 App 一致的 cmd15 等帧  
- **音乐伴舞**：`music.py`（音频 + 底盘动作；独占串口）  
- **联调**：把 6700 事件接到 App 巡检页；验证 6000 / 6500 在真机同网下可用；整理操作手册与答辩演示流程  

## 关键链路：从摄像头到 App 告警

主演示路径可以收成一条链：

1. 摄像头取帧（默认 `video0`），按配置降分辨率 / 轻量推理，减轻和导航抢算力  
2. YOLOv5 推理；场景上收敛关注 `bottle` 等目标（模型本身是 COCO 多类）  
3. **连续 N 帧**确认后才告警，并带 **cooldown**，避免同一目标连响  
4. 触发时：蜂鸣 / 语音、截图、写一行 JSON 到 `events.jsonl`  
5. `patrol_server.py` 在 **6700** 提供健康检查与事件 / 截图 API  
6. App「智能巡检」页轮询列表，点开可看截图  

一键后台启动通常是：

```bash
cd ~/Rosmaster-App/rosmaster
bash start_patrol_host.sh --bg
curl -sf http://127.0.0.1:6700/health
```

导航另开：宿主机起容器 → 容器内 `n1` / `n2` / `n3` → RViz 设 **2D Pose Estimate** 与 **2D Goal Pose**。App 用「保存并进入（巡检模式）」即可看留痕。

## 资源互斥：先读这张表再演示

边走边检能跑通，前提是承认硬件上的互斥，而不是指望「全开」：

| 不要同时开 | 原因 |
|------------|------|
| `ros/run` 与 Docker 导航 n1 | 争用底盘串口 |
| 6500 视频与 YOLO 巡检 | 争用 USB 摄像头 |
| `music.py` 与导航 / `ros/run` | 争用串口 |
| App 与 G29 同时控车 | 共用 TCP 6000，指令会打架 |

| 推荐组合 | 说明 |
|----------|------|
| 导航 + 巡检 `--bg` | 主场景：边走边检；App 只看 6700 |
| 停导航 + `ros/run` + App 或 G29 | 人工遥控 |
| 单独 `music.py` | 伴舞展示 |

同协议不等于能双端同时开：TCP 保序，但不做多客户端安全仲裁。

## 踩坑一：导航和巡检「分开都好、合上就不动」

现象很典型：只开 Nav2，RViz 设点能走；加上 YOLO 巡检后，再设目标小车不动，RViz 也难出稳定绿路径。

对照实验帮助很大：**停巡检能走、开巡检不能走**。进一步排查发现，不完全是「YOLO 抢了串口」这么简单——推理本身主要吃摄像头和算力——更要命的是宿主机侧若持续 `docker exec` 轮询 `/amcl_pose`，再加上偏重的检测负载，会把导航拖垮。若巡检再直连串口做蜂鸣，还会和 Docker 里的底盘控制冲突。

后来的改法包括：

- 巡检默认 **`--bg` 后台**，与 Docker 导航并行，尽量不占底盘串口  
- **`--nav-lite`** 等轻量推理选项，降低算力争抢  
- 位姿改为 **按需读取**（例如仅在需要告警联动时读一次），而不是后台狂轮询  
- 用诊断脚本做 A/B：`check_nav_parallel.sh`、`verify_parallel_ab.sh`  

稳定后的主演示路径就是：**导航走点 + 后台巡检 + App 看 6700**。

## 踩坑二：视频没画面，不一定是 App 的锅

联调 6500 时出现过：遥控 TCP 正常，视频却黑屏；Jetson 日志提示摄像头节点打不开。

根因落在设备节点映射：普通 USB 摄像头上 `video0` 可用，`video1` 不可用，而 udev 规则曾把 `camera_depth` 指到错误节点；视频服务又按固定路径打开设备。临时 `ln -s` 能救急，重启后又被规则盖回去，需要改 rules 或服务的设备选择。

另一侧，App 用 WebView / Image 拉 MJPEG 时，还要处理明文 HTTP、引擎初始化一类问题。结论是：**先在浏览器带端口访问 `http://{IP}:6500/...`，再查 App**；控车与视频同 IP、不同端口，别绑死成「一个连不上就全坏」。

## G29 与音乐伴舞

G29 做的是输入映射，不是改车端协议：读方向盘 / 踏板轴 → 编成与 App `CarApi` 一致的 `$...#` TCP 帧 → 打到 6000。踏板模式里把离合 / 刹车 / 油门映射到前进、后退、停止等，和手机方向键语义对齐；帧长度也曾修过一次，与 App 编码不一致时车端会直接拒帧。

`music.py` 更适合单独演示：先停导航与 `ros/run`，再播音频并编排底盘动作。联调里遇到过无声音（路径、`mpg123` 管道阻塞等），用本机声卡设备验证后再和跳舞逻辑合在一起。

## 小结与还可打磨的点

智检哨兵让我把「边缘脚本 + 多端协议 + 真机资源互斥」串成了一条可答辩的闭环。自己接触最深的是：

1. 巡检：降频推理、连续帧确认、冷却、事件落盘、6700 给 App  
2. 并行：导航与检测同开时的算力 / 串口 / 位姿轮询问题  
3. 遥控：App 与 G29 共用 TCP 协议，但必须互斥使用  
4. 模式切换：巡防、遥控、伴舞各走各的启动组合  

如果继续做，会优先补 **告警后的软切换**：短暂停导航 → 允许 App / G29 短时接管 → 再恢复巡防。现在的「留痕供后续处置」已经够演示，但离「发现异物立刻人工绕障」还有一截状态机要补。
